# SaleData Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let callers attach the SmartConnect optional `SaleData` payload (sale/line-item/customer metadata) to a transaction as a strongly-typed, versioned model that the library serialises onto the wire.

**Architecture:** A version-agnostic abstract base `SmartConnectSaleData` (exposing the wire `version`) in the root namespace; the concrete schema lives in `Yort.Eftpos.SmartConnect.SaleData.V1`. `SmartConnectTransactionRequest` gains a `SaleData` property typed to the base. An internal `SaleDataSerializer` composes the `{version, saleData:{…}}` envelope, serialising the **runtime** type so derived properties are captured. `PostTransactionAsync` emits the `SaleData` form field only when the property is set.

**Tech Stack:** .NET Standard 2.0, C# (LangVersion latest), System.Text.Json 8.x (already referenced), xUnit.

## Global Constraints

- Target `netstandard2.0`; keep the public API netstandard2.0-expressible.
- Hard tabs; file-scoped namespaces; full braces (Allman).
- SaleData types are **consumer-built input** → **mutable** (object-initialiser ergonomics), unlike the immutable library-produced result types.
- JSON: camelCase property names (`JsonNamingPolicy.CamelCase`); `DateTimeOffset` → ISO 8601; null members omitted (`DefaultIgnoreCondition = WhenWritingNull`).
- **Typing rule:** model the format only where the docs specify it (`createdAt`/`updatedAt` are ISO 8601 → `DateTimeOffset?`); every field the docs type as an unformatted `string` (all monetary fields AND `quantity`) is exposed as `string`. `Money` is NOT used here (SaleData amount encoding is undocumented/unverified).
- Wire envelope: `{ "version": "1.0.0", "saleData": { … } }` — `version` at root, body nested under `saleData`, `version` absent from the nested body.
- The `SaleData` form field is added to `POST /Transaction` **only when `request.SaleData != null`**; the financial path is otherwise untouched.
- Spec: `docs/superpowers/specs/2026-06-17-saledata-design.md`.

namespace Yort.Eftpos.SmartConnect;

/// <summary>
/// Base for the optional SmartConnect <c>SaleData</c> payload attached to a transaction. Version-agnostic: the
/// concrete schema lives in a versioned namespace (e.g. <c>Yort.Eftpos.SmartConnect.SaleData.V1</c>). Typed as

/// caller's own derived type — is accepted; the library serialises the runtime type.
/// </summary>
public abstract class SmartConnectSaleData
{
	/// <summary>
	/// The wire schema version sent as the envelope's root <c>version</c> field. Excluded from the nested
	/// <c>saleData</c> body (it is composed at the root by the library).
	/// </summary>
	[JsonIgnore]
	public abstract string Version { get; }
}

```csharp
using System.Collections.Generic;
using System.Text.Json;
using System.Text.Json.Serialization;

namespace Yort.Eftpos.SmartConnect.Internal;

/// <summary>
/// Serialises a <see cref="SmartConnectSaleData"/> to the SmartConnect <c>SaleData</c> wire envelope:
/// <c>{ "version": "...", "saleData": { ... } }</c>. The body is serialised by the value's RUNTIME type (the
/// dictionary value is typed <c>object</c>), so V1 — or a caller's own derived type — emits its full property
/// set; a base-typed serialise would emit only the base.
/// </summary>
internal static class SaleDataSerializer
{
	private static readonly JsonSerializerOptions Options = new JsonSerializerOptions
	{
		PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
		DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull
	};

	public static string Serialize(SmartConnectSaleData saleData)
	{
		var envelope = new Dictionary<string, object?>(2)
		{
			["version"] = saleData.Version,
			["saleData"] = saleData
		};

		return JsonSerializer.Serialize(envelope, Options);
	}
}
```
